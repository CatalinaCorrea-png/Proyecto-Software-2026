Fortalezas

INTERNO +

Lo que ya teníamos a favor — y las nuevas fortalezas que construimos sobre esa base.

// ANÁLISIS ORIGINAL

  • IA real integrada — YOLOv8 fine-tuned propio, fusión térmica y MediaPipe.
  • Stack moderno — React 19 + TS, FastAPI, MongoDB, WebSockets, Recharts, Leaflet.
  • Hardware propio — firmware ESP32-CAM con PID, telemetría UDP y GPS.
  • Arquitectura cohesiva — Docker Compose con health checks y build de producción.
  • Equipo ágil — sprints documentados y responsabilidades separadas.

★ APRENDIZAJE · NUEVAS FORTALEZAS

  • ✓Backend modular — sobre la arquitectura cohesiva, separamos en routers/ · core/ · db/ · modules/.
  • ✓Suite de tests propia — 6 módulos con pytest cubriendo fusión, grid, misiones, modelos y estado.
  • ✓Onboarding documentado — README con guía completa, Swagger activo en /docs y .env.example.
  • ✓La matriz validó las bases — confirmar las fortalezas nos dio confianza para refactorizar sin romper lo bueno.
🔧

Debilidades

INTERNO −

El cuadrante de mayor impacto: la matriz lo convirtió en un backlog priorizado que ya atacamos.

// ANÁLISIS ORIGINAL

  • Cobertura de tests baja — riesgo de regresiones silenciosas.
  • Backend monolítico — main.py con 904 líneas, difícil de testear.
  • Seguridad ausente — .env vacío, credenciales hardcodeadas, sin auth.
  • Documentación escasa — README básico, API no documentada.
  • Modelos binarios en git · dual-DB sin estrategia.

★ APRENDIZAJE · QUÉ ATACAMOS

  • ✓Tests (prioridad #1) — backend/tests/ con rutas críticas (test_missions_api) + pytest.ini.
  • ✓Backend desacoplado — main.py pasó de 904 → 56 líneas, repartido por responsabilidad.
  • ✓Credenciales fuera de git — .env.example + .env ignorado; ya no hay secretos hardcodeados.
  • ✓Dual-DB explícito — routers missions_mongo / missions_sql separados y organizados.
  • ⧗Pendiente consciente — modelos .pt a Git LFS y autenticación de API (priorizados, en backlog).

Amenazas

EXTERNO −

Riesgos que vigilamos: algunos los desactivamos a tiempo, otros siguen en el radar.

// ANÁLISIS ORIGINAL

  • Dependencia de hardware — sin el ESP32, partes corren solo simuladas.
  • Latencia de ML sin medir — sin benchmarks de tiempo real.
  • Deuda técnica acumulable — sin tests y con main.py monolítico.
  • Datos sensibles expuestos — imágenes sin cifrar (GDPR).
  • CI/CD incompleto — Actions solo compila el firmware.

★ APRENDIZAJE · DESACTIVADAS vs. VIGENTES

  • ✓Deuda técnica frenada a tiempo — sumar tests y modularizar evitó que se acumulara hacia el final.
  • ⧗CI/CD — sigue solo hardware.yml; falta validar backend y frontend en cada push.
  • ⧗Latencia ML — aún sin benchmarks de inferencia en tiempo real.
  • ⧗Datos sensibles — imágenes todavía sin cifrado; ligado a la auth pendiente.
